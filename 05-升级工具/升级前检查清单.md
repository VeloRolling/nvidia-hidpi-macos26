# 升级 NVIDIA 驱动前的准备清单

> 适用：把现役 nullmoth 2.4.3 + planE 版 NVRM，换成新版源码编译的版本，同时保留 2× HiDPI。
> 本机基线（2026-10-21 核对）：macOS 26.7.1 (25G241) / RTX 3060 Laptop 6GB / 3520×1980 → 界面 1760×990 @165Hz。

---

## 0. 先确认：这次真的值得升吗

只有三种情况值得花这半小时：

| 情况 | 说明 |
|---|---|
| 作者仓库发了新版，且修了你在意的 bug | 值得，但要重新验证一遍所有挡位 |
| macOS 大版本升级把 AuxKC 冲了 | 必须重做，不升也得升 |
| 你现在有具体故障（黑屏、掉帧、切档弹回） | 可以拿新版试，但要先备份 |

**只是"看到新版想装"——别动。** 当前这套是跑通的，换版本唯一确定的变化是"要再验证一遍"，收益不确定。

---

## 1. 前置条件核对（本机已全部满足）

| 项目 | 要求 | 核对命令 |
|---|---|---|
| SIP | `Kext Signing: disabled` | `csrutil status` |
| Xcode 命令行工具 | 有 clang / make / libtool / xcrun | `xcrun --find clang` |
| 磁盘空间 | 根分区 ≥ 5GB（编译产物约 3GB） | `df -g /` |
| 系统 KC | 三个文件都在 | `ls /System/Library/KernelCollections /Library/KernelCollections` |
| 作者驱动仓库 | `~/nvdrv-src/kexts/NVRM/rmcc.py` 存在 | `ls ~/nvdrv-src/kexts/NVRM` |
| 新版 OGKM 源码 | 有 `version.mk` 和 `src/nvidia-modeset/kapi/src/nvkms-kapi.c` | `ls <源码目录>/version.mk` |
| **启动参数** | boot-args 里有 `nvfbhidpi=1` | `nvram boot-args` |

最后一条最容易忘：**没有 `nvfbhidpi=1`，override 里的挡位根本不会被驱动放出来**，你会误以为"新驱动把功能搞坏了"。这一项在 OpenCore 的 `config.plist` 里，换驱动时不用动它。

---

## 2. 备份（没做完别往下走）

升级脚本会自动备份到 `~/Desktop/NVRM升级备份-<时间戳>/`，包含：

```
NVRM.kext.bak                      现役 planE 版驱动
NVRMFB.kext.bak                    现役帧缓冲
AuxiliaryKernelExtensions.kc.bak   现役辅助内核集合
显示状态-升级前.txt                   system_profiler 快照
已加载kext-升级前.txt                 kmutil 视角的版本/依赖
boot-args.txt                      启动参数
upgrade.log                        全过程日志
```

**再手工拷一份到 U 盘或另一台机器。** 新驱动起不来时进不了图形界面，只能靠恢复模式或另一台机；手上没有离线副本，就只剩下重装系统这一条路。

另外这两样也别丢（不在脚本备份范围内）：

```bash
sudo cp "/Library/Displays/Contents/Resources/Overrides/DisplayVendorID-9e5/DisplayProductID-a07" ~/Desktop/
sudo cp -R /Library/Extensions/NVRMAGDC.kext /Library/Extensions/NVAccel.kext ~/Desktop/
```

## 3. 记下基线（升级后逐条对比，一眼看出哪层坏了）

```bash
# ① 现在到底是不是 2×（唯一可靠判据）
system_profiler SPDisplaysDataType | grep -E "Resolution|UI Looks like"

# ② 哪些 nullmoth kext 真的加载了
kmutil showloaded --list-only --arch x86_64 | grep -i nullmoth

# ③ 启动参数（确认 nvfbhidpi=1 还在）
nvram boot-args

# ④ 现役 NVRM 的指纹（升级后应与备份文件不同、与构建产物相同）
shasum -a 256 /Library/Extensions/NVRM.kext/Contents/MacOS/NVRM

# ⑤ AuxKC 里确实有 NVRM（注意必须带 -A，否则读的是仓库，会给假 OK）
kmutil inspect -a x86_64 -A /Library/KernelCollections/AuxiliaryKernelExtensions.kc | grep -c com.nullmoth.NVRM
```

把 ①③ 输出粘到备忘录里。升级后如果 ① 变成两个相等（1×），说明 planE 没进内核；如果 ③ 少了 `nvfbhidpi=1`，说明 EFI 被改过。

---

## 4. 确认救援预案（本机没有自动回滚）

已核实 `/Library/NullMoth/` 里的两个脚本：

- `bootguard.sh` — 只在桌面起来且稳定 45 秒后写「本次启动成功」标记，**不计数失败**
- `nullmoth-recover.sh` — **只**在 NVRAM 出现 `nullmoth-remove` 时才卸载驱动并重启

也就是说：**没有"连续几次启动失败自动回滚"**。真正能救命的只有三条：

| 手段 | 操作 |
|---|---|
| 卸掉驱动（最省事） | 进恢复模式 → 终端 → `nvram 7C436110-AB2A-4BBB-A880-FE41995C9F82:nullmoth-remove=1` → 重启，驱动自动卸载 |
| 换回旧 AuxKC | 进恢复模式 → 终端 → 挂载数据卷 → 把备份的 `.kc` 覆盖回 `/Library/KernelCollections/AuxiliaryKernelExtensions.kc` |
| OpenCore 兜底 | 用另一台机或 U 盘上的 OpenCore，改 `boot-args` 去掉 `nvfbhidpi=1` 或加调试参数，先进系统再修 |

**动手前先确认自己进得了恢复模式**（开机按 Cmd+R，能到「macOS 恢复」界面就行）。进不去就先别升级。

## 5. 开始升级

```bash
cd ~/Desktop/HiDPI修复包-macOS26/05-升级工具

# 先只体检，不碰任何文件（推荐每次都先跑一遍）
./升级NVRM.command --check /路径/到/open-gpu-kernel-modules

# 正式升级（双击也行，再把源码目录拖进窗口）
./升级NVRM.command /路径/到/open-gpu-kernel-modules
```

脚本会依次做 7 步，其中**只有第 7 步会写系统**：

1. 环境自检（SIP / clang / 空间 / KC / 仓库 / 补丁文件）
2. 校验源码树、读版本号、比对 `CXXFILES` 与仓库源文件
3. 备份四样东西到桌面
4. 试打 planE 补丁（能干净应用才动手；不匹配就停下并打印需要手改的 4 处）
5. 生成编译命令表 → 并行编译 → 归档 `libnvkernel.a` / `libnvkms.a`
6. 重链接 `NVRM.kext`（可选同时重建 `NVRMFB.kext`）→ ad-hoc 签名
7. `ditto` 安装 → `chown root:wheel`（**陷阱 1**）→ `kmutil create` 写新 AuxKC → `kmutil inspect -A` 确认 `com.nullmoth.NVRM` 在包里（**陷阱 2**）→ 才替换现役 AuxKC

第 7 步任何一环失败会**自动还原旧 AuxKC** 并拒绝重启，系统保持原样。

## 6. 重启后验证（三条都过才算成功）

```bash
# ① 必须是 2:1（3520 / 1760）
system_profiler SPDisplaysDataType | grep -E "Resolution|UI Looks like"

# ② 版本变了，且三个 kext 都加载
kmutil showloaded --list-only --arch x86_64 | grep -i nullmoth

# ③ 缩放提交成功（出现 -> 1 或 COMMIT）
log show --last 5m --predicate 'eventMessage CONTAINS "switchMode"' 2>/dev/null | tail -5
```

再双击 `03-脚本/检测HiDPI.command`，确认 2880～3520 那几档还在（新版驱动如果改了 `validateDetailedTiming`，挡位可能变多或变少）。

## 7. 失败分级处置

| 现象 | 最可能的原因 | 处置 |
|---|---|---|
| 卡在苹果标 / 黑屏，进不了桌面 | 新 NVRM 加载即崩 | 恢复模式 → `nullmoth-remove=1` → 重启，装回备份 |
| 能进桌面，但界面变成 1×（Resolution = UI） | planE 没编进去 | `shasum` 比对 `/Library/Extensions` 里的二进制与 `~/nvbuild-out-*/NVRM.kext`，不一致就是安装没成功 |
| 挡位列表变少 | 新版改了缩放器上限 | 回到 `--check` 阶段，确认 override 7 条还在 |
| 切换挡位弹回原样 | 走了 head scaler 之外的路径 | 看 dmesg 里 per-head status 是否 6，属于补丁需重写的范畴 |
| `kmutil create` 报 `could not find a kext which exports this symbol` | `CXXFILES` 少文件（历史坑：漏 `nv_xnu_power.cpp`） | 对比脚本列表与 `~/nvdrv-src/kexts/NVRM/*.cpp`，补齐后重跑 |

---

## 8. 一句话总结

**备份拷到 U 盘 → 确认进得了恢复模式 → 先跑 `--check` → 再跑正式升级 → 重启后对比 Resolution 与 UI Looks like。**
